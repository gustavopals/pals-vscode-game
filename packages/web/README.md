# @lotg/web

O cliente do jogo: um app web com aparência de editor de código (barra de atividades, árvore lateral, abas, barra de status, paleta de comandos e avisos no canto). Decisão e motivos no [ADR 0008](../../docs/decisions/0008-cliente-web-com-aparencia-de-editor.md).

O app **só exibe**. Toda regra e toda conta vêm do servidor, dentro do `ViewState`; importar `@lotg/engine` aqui é barrado pelo lint. Não usa o nome, o logotipo nem nada do Visual Studio Code: só os Codicons (CC BY 4.0), empacotados junto.

## Rodar

```bash
pnpm dev:up && pnpm dev:api    # banco e API em http://localhost:3000
pnpm dev:web                   # http://localhost:5173, com /v1 repassado para a API
```

`LOTG_API_URL` troca o destino do repasse (padrão `http://localhost:3000`). Em produção não há repasse dentro do app: ele e a API ficam na mesma origem, e quem separa `/v1` é o proxy da plataforma ([ADR 0009](../../docs/decisions/0009-implantacao-no-coolify.md)).

```bash
pnpm --filter @lotg/web build   # packages/web/dist, com hash no nome dos arquivos
pnpm docker:build:web           # imagem com o Caddy servindo o dist na porta 80
```

## Testar

```bash
pnpm --filter @lotg/web test                # testes de unidade (sem navegador)
pnpm --filter @lotg/web test -- controller  # só os arquivos com "controller" no nome
pnpm dev:up && pnpm test:e2e                # Chromium de verdade, API de verdade, db_test
pnpm test:e2e 04-conta -g "duas abas"       # um arquivo, um teste
GAME_TIME_SCALE=3 pnpm test:e2e 03-retorno-e-conexao -g "ritmo"   # o ritmo Rápido com o servidor de teste como o da produção
```

Os testes de unidade rodam em Node, sem DOM: funções puras e HTML gerado com `preact-render-to-string`. Tudo o que depende de um navegador (foco, teclado, `localStorage` entre abas, CSP, contraste) é provado em `tests/e2e/`, com o app compilado. `src/test-helpers.ts` tem uma API `/v1` de mentira em memória (`fakeApi`), um controlador pronto (`makeController`) e diálogos respondidos por roteiro (`scriptedDialogs`).

Os testes em navegador rodam com o servidor de teste no ritmo Normal, o dos tempos do GDD. Os cenários "no ritmo da produção" de `tests/e2e/03-retorno-e-conexao.spec.ts` fundam o feudo no ritmo Rápido pelas boas-vindas e rodam com a suíte: conferem que os prazos e as taxas na tela são os que a API entregou e que a obra termina na hora anunciada. `GAME_TIME_SCALE=3` sobe o servidor de teste com o padrão da produção (o Rápido já vem marcado); assim só esses cenários valem, e um servidor de teste que tenha ficado de pé na porta 3100 precisa ser encerrado antes, porque o Playwright reaproveita o que encontra.

**O tempo nos testes em navegador.** `world.passTime(ms, ...páginas)` (`tests/e2e/helpers.ts`) adianta o relógio do servidor e o de cada página e só volta com a página em repouso. Antes de saltar, espera as chamadas à API que a página ainda tem em voo: o resultado de uma ordem aparece na tela antes de terminar a leitura dos eventos que a segue. Depois do salto, espera o ciclo que ele dispara, e só conta o que a página pediu depois dele: a leitura da visão (que renova a sessão quando o access token venceu, e ele vale 15 minutos) e, em seguida, a dos eventos. A resposta de uma leitura anterior ao salto não é o ciclo; quem lesse o servidor logo depois dela (`session`, `pendingCards`, `gameEvents`) usaria o access token vencido. O cenário "com a rede lenta" de `07-conselho.spec.ts` segura essa garantia. `world.jump` não espera nada: é para páginas sem sessão ou sem rede.

**Os lobos nos testes em navegador.** Toda partida nova tem os uivos na hora 18 de jogo e a incursão do roteiro na hora 30 (no ritmo Normal), e depois dela as incursões por Ameaça; elas mexem nos estoques, nos braços, na moral, nos avisos e na barra de status. Como o Conselho, a Horda fica **calada** por padrão: quando a página funda um feudo, `tests/e2e/helpers.ts` manda o servidor de teste trocar as incursões marcadas por uma só, para daqui a mil anos de jogo (`/__test/horde-quiet`, o mesmo que `quietHorde` faz nos testes de integração do servidor), antes de a resposta chegar à página. Os cenários da incursão, em `08-ameaca.spec.ts`, chamam `world.wolvesRoam()` antes de fundar o feudo. Para ter a Torre de Vigia ou a Paliçada de pé antes da hora dos lobos sem jogar as dezenas de horas que o Salão leva para liberá-las, `world.raise('palisade', 1)` põe o edifício no nível pedido direto no estado (`/__test/raise`); daí em diante o aviso, a defesa e o desfecho são os do motor. O cenário dos dez objetivos pelo teclado, em `05-teclado-e-temas.spec.ts`, joga a partida de verdade e usa o mesmo atalho uma vez, para o Salão no nível 3 (o que libera a Paliçada); o do aviso único dos objetivos, em `06-avisos-e-preferencias.spec.ts`, para o Salão no nível 2. `serverView`, de `helpers.ts`, lê do servidor a visão inteira que a tela deve mostrar.

**O Conselho nos testes em navegador.** As cartas chegam por sorteio, de 8 em 8 horas no ritmo Normal, e mexem na moral, nos avisos e na barra de status. Para os cenários que não são sobre o Conselho não dependerem de qual carta a semente tirou, o conselho fica **em recesso** por padrão: quando a página funda um feudo, `tests/e2e/helpers.ts` manda o servidor de teste adiar o próximo sorteio para um futuro que teste nenhum alcança (`/__test/council-recess`), antes de a resposta chegar à página. Os testes de `07-conselho.spec.ts` chamam `world.conveneCouncil()` antes de fundar o feudo: o sorteio volta a valer e o feudo nasce de uma semente fixa (o servidor de teste aceita `seed` em `POST /games`), para as cartas serem as mesmas a cada execução. Esses testes não citam carta nenhuma: leem do servidor a que está na mesa e conferem que a tela mostra o que ele mandou, porque o catálogo cresce. Quando um cenário precisa de uma carta certa (a que tem continuação, no teste dos três blocos de `03-retorno-e-conexao.spec.ts`), ele deixa o conselho em recesso e a põe na mesa pelo identificador, com o prazo que quiser (`/__test/council-deal`): a carta entra como chegaria do sorteio, e daí em diante a resposta, a expiração e a continuação são as do motor. `session`, `pendingCards` e `gameEvents`, de `helpers.ts`, leem do servidor o que a tela deve mostrar.

O `ViewState` de exemplo dos testes é o golden do motor, importado por caminho relativo (`../../engine/src/__golden__/view-seed-pedra-alta.json`).

`src/bundle.test.ts` compila o app de verdade (em memória, sem gravar `dist`) e confere que o JavaScript servido não leva número nem frase de `@lotg/content`: do conteúdo só entram as listas de identificadores que os schemas do protocolo usam. O que mantém o resto de fora é o descarte de código sem uso do build, e basta um módulo de `@lotg/protocol` que o app carrega ler `balance` em tempo de execução para a tabela inteira ir junto. Conteúdo novo que não pode chegar ao jogador antes da hora (efeitos de cartas, composição de incursões) fica coberto pelo mesmo teste, desde que seja exportado por `@lotg/content`. O teste também procura, pelo nome, o que o Conselho e a Ameaça escondem: as flags, as frases dos efeitos escondidos e as chaves do catálogo de cartas e das incursões. E o lint avisa antes do build: fora dos testes, o app não importa `@lotg/content` nem o `contentHash` de `@lotg/protocol`, que lê o conteúdo inteiro e é só do servidor e do simulador.

## Dificuldade e ritmo (GDD §13.9)

- **As opções vêm do servidor.** `controller.loadCatalog()` lê `GET /v1/catalog` (sem sessão) e guarda `newGame` em `controller.catalog`: rótulos, frases, a marca de recomendado e `defaults`, que é o que vem marcado. O app não escreve rótulo, frase nem número de regra, e marca por `defaults`, não por `recommended` (o servidor de teste roda no ritmo Normal). A resposta é sempre conferida com `CatalogResponseSchema`, também em produção.
- **Só é lido quando a tela usa:** boas-vindas, Preferências e o comando "Nova partida". Quem tem feudo e não passa por aí nunca o pede.
- **Sem catálogo, nada quebra.** Sem ligação, ou com um servidor de uma versão anterior (404), as boas-vindas ficam como na v0.1, "Nova partida" não pergunta nada, e o corpo de `POST /games` vai sem `difficulty` nem `timeScale`: valem os padrões do servidor. Com catálogo, o corpo leva o que a tela mostrava marcado.
- **"Nova partida" espera o catálogo antes do primeiro diálogo, e roda um fluxo por vez.** Nessa espera não há diálogo na tela para barrar um segundo acionamento; o comando tem uma trava (`startingNewGame`, em `palette/commands.ts`) e relê a conta depois da espera. Sem a trava, dois fluxos se intercalavam na fila de diálogos e o segundo feudo fundado arquivava o primeiro.
- **"Jogar agora" continua a um clique.** As opções já vêm marcadas e escolher é opcional; o botão não espera o catálogo. Cada grupo é um `radiogroup` de botões de rádio nativos: uma parada do `Tab`, setas para trocar. O nome de cada opção é a linha curta; a frase é a descrição (`aria-describedby`), sempre à vista.
- **"Nova partida"** pergunta os dois em listas de escolha com o padrão já marcado (`Enter`, `Enter`), antes da confirmação, que repete a escolha ao lado do aviso de que o feudo atual é arquivado.
- **Nas Preferências**, "Dificuldade: … · Ritmo: … (não mudam durante o ano)" vem de `settlement.difficultyLabel` e `settlement.paceLabel` do `ViewState`; a frase do que a dificuldade muda vem do catálogo, pelo `settlement.difficulty`.

## Estações, lenha e frio (GDD §4.1)

Tudo vem pronto no `ViewState`; o app não escreve fator, taxa nem prazo.

- **O que a estação muda** fica à vista no cabeçalho (`calendar.seasonEffects`) e na explicação do item do feudo na árvore. O fator de cada taxa já vem dentro do `breakdown` ("× 1,3 (outono)", "× 0,8 (frio)", "−9/h (lenha de 18 habitantes)"), que a tabela de recursos, o painel de trabalhadores e a árvore mostram como sempre mostraram.
- **A conta da lenha** (`components/Banners.tsx`, `FirewoodNote`) aparece sem ninguém pedir: no outono é `calendar.nextSeason.firewood` (o inverno inteiro, visto de antes: quanto guardar); antes do outono, só quando o inverno chega em menos de um dia de relógio e a madeira não basta (`firewoodSeasonSoon`, sobre `calendar.nextFirewoodSeason`: no ritmo Rápido, o fim do verão); no inverno é `winter.firewood` (o que falta até a estação virar). Com `missing` maior que zero ganha o destaque de aviso. É `role="note"`, não região viva: os números mudam a cada leitura.
- **No inverno** o cabeçalho e a árvore ganham a linha da Lareira: `winter.firewoodPerHour` e, se a lenha não chega até a primavera, em quanto tempo a madeira acaba.
- **"Acaba em"** passa por `runsOutIn` (`ui/format.ts`). É o `depletesInSeconds` da visão, menos em um caso: a madeira do inverno com `winter.firewood.missing` igual a zero. Aquele prazo é o estoque pela taxa de agora e não olha o calendário; a lareira apaga na virada da estação, e anunciar "acaba em 4 dias" a um dia da primavera seria alarme falso. Se o motor passar a devolver `null` nesse caso, a função vira só um repasse. Na **comida**, a virada de estação muda o que a Fazenda rende: quando a linha não tem prazo, ou tem um prazo que cai depois da virada, vale a previsão do servidor para a estação que vem (`calendar.nextSeason.food.depletesInSeconds`, que já conta a partir de agora). A comida que cresce no outono e acaba no começo do inverno aparece então como "acaba em 8 h" na tabela, na árvore e em "Antes de partir", e `runsOutWhy` devolve a frase da previsão, que vira a explicação do prazo. O app não faz a conta: só escolhe qual dos dois prazos do servidor mostrar.
- **O frio** (`winter.cold`) tem ícone (`flame`) e texto próprios em todo lugar, para não se confundir com a fome: aviso no painel (`ColdBanner`, nas abas Feudo e Hoje), "· frio" e a Lareira na árvore, e a barra de status (`$(flame) Frio em …`; com fome ao mesmo tempo, `Fome e frio em …`, e a explicação traz os dois textos). O destaque de cor é o mesmo da fome; quem distingue é o ícone e o texto.
- **Avisos** (`notifications/policy.ts`): `coldStarted` e `famineStarted` são alarmes (tom de aviso, passam na frente); `coldEnded` e `famineEnded` são o alívio deles e chegam no mesmo nível "Essenciais", com tom de informação. Com pouco espaço: alarmes, alívios, o resto. O texto é a frase da Crônica que veio no evento.
- **Prazos da estação**: `durationNote` das obras aparece uma vez acima das listas "Melhorar" e "Construir", uma vez na lista da paleta e na explicação de cada obra na árvore; o do recrutamento, ao lado do prazo, no painel e na paleta.
- **A explicação de um número** (`.explained`) fica por cima dos avisos do canto. O aviso de frio ou de fome não some sozinho, e antes cobria a ponta da explicação em telas estreitas.
- Os prazos aproximados ("acaba em 14 h", "Inverno em 4 h", "frio há 50 min") não descem com o relógio local: o cabeçalho, a tabela e a árvore mostram o mesmo número, que muda a cada leitura do servidor.

## Armazenamento: limite, "cheio em" e desperdício (GDD §5.5)

O limite, a previsão, o que se perde e a frase do que fazer vêm prontos em `resources[]` do `ViewState`. O app não conhece capacidade, fator de dificuldade nem regra de corte.

- **Tabela de recursos** (`components/ResourcesTable.tsx`): as colunas Estoque e Cap do GDD §13.3; o limite é um número com explicação (`capExplanation`: "Despensa: 500 iniciais", "Celeiro Nv2: 1.500"). A tendência diz, nesta ordem: "acaba em", "cheio: a produção está se perdendo", "cheio", "cheio em 6 h", "crescendo", "caindo", "em falta", "estável". "Crescendo" sem previsão de encher e "cheio" acima do limite levam a frase do servidor como explicação (`fullNote`).
- **O destaque de "cheio em"** é ícone e texto, abaixo de 8 horas (`FULL_SOON_SECONDS`, em `ui/format.ts`). É escolha de apresentação, não regra: o tamanho de uma ausência comum (GDD §2.3). O prazo já vem em horas de relógio.
- **A saída ao lado** (`StorageNotes`, abaixo da tabela): cada depósito cheio, ou a menos de 8 h de encher, ganha um aviso com a frase, o custo, o prazo e o efeito da obra (`constructions.available[].effect`) e o botão "Construir Celeiro" ou "Ampliar Armazém", que chama `lords.build` com o `storageBuilding` do recurso. A madeira e a pedra dividem o Armazém: um aviso, um botão. Bloqueada, a obra deixa o botão desabilitado, com o motivo; com a obra do depósito em andamento, o botão some. Não é região viva nem `role="note"`.
- **Árvore** (`ui/treeModel.ts`): "655/900 (+55/h)" em cada recurso. Com o depósito cheio e perdendo, ou a menos de 8 h de encher, o alerta toma o lugar da taxa ("655/900 ⚠ cheio em 4 h", "900/900 ⚠ cheio, perde 55/h") e se repete na linha "Recursos". A previsão distante fica só na tabela: a barra lateral é estreita.
- **Construir e melhorar** (`ConstructionsPanel.tsx`): uma obra com `fromLevel` 0 é um edifício que ainda não existe. Ela fica na lista "Construir", o botão diz "Construir" e o nome nunca fala em "Nv0" (`upgradeName`: "Construir: Celeiro" na árvore, na paleta e nas planejadas). As outras ficam em "Melhorar". O que a obra muda aparece abaixo do custo.
- **Cancelar uma obra** diz o que volta e o que se perderia (`refundSentence`, com `refund[].amount` e `lost`), no painel, na árvore e na confirmação.
- **Relatório de Retorno** (`game/returnReport.ts`, `components/Today.tsx`): a tabela abre a conta de cada recurso, `antes + produção − gasto + recebido − perdido = agora`. Gasto, recebido e perdido são somas dos totais que os eventos trazem em `data` (`spent_*`, `gained_*`, `wasted_*`). O perdido soma os fechos diários (`storageWasted`) e a diferença do contador `wastedToday` entre a visão guardada e a de agora, e por isso aparece mesmo sem virada de dia na ausência. A coluna Produção mostra o que o feudo rendeu, descontado o consumo: `produced` (o que entrou no estoque, como o protocolo define) mais a produção que não coube, que é o perdido menos `cut`. `cut` é o que uma recompensa ou uma devolução perdeu no limite do depósito (`lost_*`, no evento do próprio ganho): nunca foi produção. A coluna Recebido mostra o ganho inteiro (`received + cut`), e o corte fica no Perdido, que nunca é menor que ele. Onde a perda aconteceu e o que fazer estão no bloco "O que exigiu um preço", montado dos mesmos números (ver "Relatório de Retorno em três blocos"). Os fechos diários não viram linha em lugar nenhum.
- **Crônica recente**: `isChronicleEvent` usa `CHRONICLE_HIDDEN_EVENT_TYPES` do protocolo (viradas de dia e fechos do desperdício ficam fora).
- **Avisos**: `storageFilled` e `buildingFounded` avisam no nível "Todas"; nenhum dos dois é alarme.
- **Sem a visão guardada** (cache de outra versão do app), o relatório não tem linhas de estoque e, por isso, não tem a linha de desperdício daquela ausência.

## Filas de obras e planejadas automáticas (GDD §6.3)

As filas, a marca de cada planejada, o que ela espera e o prazo vêm prontos em `constructions` do `ViewState`. O app não conhece o nível que abre a segunda fila, a ordem em que o motor tenta as planejadas nem a conta do prazo.

- **Uma linha por fila aberta** (`components/ConstructionsPanel.tsx`, `QueueRow`), a partir de `constructions.queues`: a obra em curso, com contagem regressiva, progresso, "Cancelar" e o que o cancelamento devolve, ou "Os pedreiros estão livres.". Com duas filas abertas cada linha leva o número da sua ("Fila 1", "Fila 2"), e cada "Cancelar" tem o nome da obra (`aria-label`). `constructions.active` continua na visão, mas nada no app depende dele: quem quer "a obra" usa `busyQueues` ou `soonestConstruction` (`ui/format.ts`).
- **A fila que ainda não abriu** aparece com o motivo, que é `constructions.queuesNote`, e um cadeado ao lado do texto; nunca como botão desabilitado. A mesma frase é a explicação da linha "Construções" na árvore. Com a fila ocupada, cada obra disponível mostra a recusa do servidor (`QUEUE_LOCKED`), que também diz o que abre a segunda.
- **Planejadas**, em uma lista ordenada (a ordem é a em que as automáticas são tentadas), com uma frase que diz isso. Cada uma tem o orçamento, o prazo da obra, a marca **"Iniciar quando houver recursos"**, a linha de espera e "Tirar da lista". A manual que já pode começar (`waiting` nula) diz "Pode começar agora." e ganha o botão "Iniciar agora".
- **A marca é uma caixa de seleção que só muda quando o servidor confirma.** O clique manda `setAutoStart` e cancela a troca local (`preventDefault`): a caixa mostra `planned[].autoStart`, nunca um palpite. Uma recusa (`NOT_PLANNED`, a obra começou nesse meio) deixa a caixa como estava e vira aviso.
- **Planejar e marcar dizem o nível que a tela mostra.** `planConstruction` e `setAutoStart` levam `targetLevel` (o de `available[]` ou de `planned[]`), no painel e na paleta. Com a tela atrasada (outra aba já planejou ou iniciou a obra), o servidor recusa com a frase pronta (`ALREADY_UPGRADING`, `MAX_LEVEL` ou `STALE_LEVEL`) em vez de planejar, e pagar, o nível seguinte; a recusa traz a visão nova, e a lista se corrige sozinha.
- **A linha de espera** é `planWaiting` (`ui/format.ts`): `waiting.text` e, quando `etaSeconds` não é nulo, ": em " mais a duração. O prazo desce com o relógio da página, como a contagem das filas; o painel põe maiúscula e ponto, a árvore usa a frase como veio.
- **A leitura seguinte acontece quando a espera acaba.** `nextPollMs` (`game/gameSession.ts`) olha o prazo de cada fila e o `etaSeconds` de cada planejada: a obra que começa sozinha aparece na hora, sem esperar os 30 s do ciclo.
- **Árvore** (`ui/treeModel.ts`): uma linha por obra em curso (`active:<edifício>`), o grupo "Planejadas" ("2 automáticas, 1 manual") com uma linha por planejada ("Serraria → Nv3", "automática · espera 30 de madeira: em 1 h 15 min"), e as obras disponíveis. A linha "Construções" resume: as obras em curso, a fila que sobra e quantas planejadas há. O botão da linha da planejada troca a marca ("Iniciar sozinha" ou "Esperar ordem"); o da obra em curso cancela aquela obra.
- **Barra de status**: a obra que termina primeiro, esteja em que fila estiver, e "+1 obra" quando há outra.
- **Paleta** (`palette/commands.ts`): "Planejar obras" pergunta, depois da obra, se ela começa sozinha. Para a obra que ainda não pode começar, "Iniciar quando houver recursos" já vem marcada (`Enter`, `Enter`). Se a obra já pode começar, a opção avisa que ela começa agora mesmo, e o que vem marcado é "Só deixar na lista": o padrão nunca gasta. "Planejadas: ligar ou desligar o início automático" lista as planejadas com o que o clique faz e o que cada uma espera. "Cancelar a obra em andamento", com duas em curso, pergunta qual.
- **Crônica, avisos e relatório**: `constructionAutoStarted` é linha da Crônica; avisa no nível "Todas", como o fim de uma obra (a obra que o próprio jogador ordena não avisa); e no Relatório de Retorno entra na lista do que ler, com o custo somado ao gasto de cada recurso pelos `spent_*` do evento.

## Troca de ofício e experiência (GDD §5.3 e §5.4)

As regras em frase, o prazo da adaptação, o que rende um trabalhador adaptado e um recém-chegado, as levas em adaptação, a experiência de cada ofício e o porquê da tendência vêm prontos em `workersRules` e `workers[]` do `ViewState`. O app não conhece a fração da adaptação, o ganho diário de experiência nem o bônus da mestria. As frases e as contas de apresentação ficam em `ui/workers.ts`.

- **O custo da troca fica à vista antes de qualquer clique**, sem diálogo no "+" e no "−". No painel (`components/WorkersPanel.tsx`): as duas frases do servidor (`adaptationText` e `removalText`) abaixo do título, e em cada edifício "+1 aqui: +4/h agora, +8/h depois de 2 h" (`nextWorkerGain`: `perNewWorkerPerHour`, `perWorkerPerHour` e `workersRules.adaptationSeconds`). O botão "+" aponta para essa frase (`aria-describedby`). Na árvore, a mesma frase vai na dica do "+" (`TreeNode.actionHints`, `actionTitle` em `workbench/Tree.tsx`) e na explicação da linha.
- **Quem se adapta**: "2 em adaptação por mais 38:00, rendendo 10,2/h cada", uma parte por leva quando há mais de uma (`adaptationLine`, a partir de `adaptingCohorts`). A contagem desce com o relógio da página. A árvore e a lista da paleta dizem só "2 em adaptação". A conta da taxa (`breakdown`) já traz a adaptação e a mestria, e é mostrada como sempre foi.
- **A leitura seguinte acontece quando a primeira leva termina** (`nextPollMs`, em `game/gameSession.ts`): o fim da adaptação não gera evento, e sem isso a taxa só subiria na tela no ciclo seguinte.
- **Experiência**: "Experiência 40/100, subindo · +12% de produção" e uma barra (`<progress>`, com rótulo), ou "Ofício dominado · +30% de produção" no fim da barra (`workersRules.experienceMax`). A tendência é dita por palavra; a seta só acompanha. A explicação do número é `experienceNote` (o porquê deste edifício) seguida de `workersRules.experienceText` (a regra).
- **Quando a experiência pede uma ação** (`experienceNeedsAttention`: está caindo, ou parou com gente trabalhando e a barra por encher), a frase do servidor sai da explicação e fica à vista na linha, com ícone de aviso. O edifício vazio que nunca teve ofício não tem o que perder e não ganha aviso. Na árvore, o edifício que perde o ofício diz "⚠ o ofício se perde".
- **Lista "Alocar trabalhadores"** (`palette/commands.ts`): o campo de busca mostra os livres e `adaptationText`; cada edifício, quantos trabalham, quanto rendem, quem se adapta e o "+1". No campo do número, a frase muda a cada tecla (`allocationMessage`): "+2: 81,5/h agora, 122,3/h depois da adaptação (2 h)", seguida da regra da chegada ou, ao tirar de onde há gente em adaptação, da regra da saída.
- **A prévia é do app** (`previewAllocation`): soma as duas taxas da visão e, ao tirar, desconta primeiro das levas mais novas, como `removalText` diz. Quem decide é o servidor; se a ordem de saída mudar no motor, a prévia precisa mudar junto (o teste em navegador da troca de ofício tira um trabalhador de um edifício com gente adaptada e em adaptação e confere a prévia com a taxa que o servidor devolve).
- **Avisos e Crônica**: `craftMastered` é linha da Crônica e avisa no nível "Todas", com uma estrela (`star-full`). O fim da adaptação não avisa.
- **Cache**: `workersRules` e os campos novos de `workers[]` são obrigatórios no schema; a visão guardada pela versão anterior é descartada sem mexer em `VIEW_FORMAT`.

## Moral (GDD §5.6 e §5.7)

O número, a faixa, o fator na produção, a conta termo a termo, o que a próxima virada do dia vai fazer, o conselho e o que as viradas fazem com o povo vêm prontos em `morale` do `ViewState`. O app não conhece os limites das faixas, o peso de termo nenhum, as chances de alguém chegar ou partir nem o piso de população. As frases de ligação e as escolhas de apresentação ficam em `ui/morale.ts`.

- **A moral só muda na virada do dia, e a tela separa as duas coisas.** `value`, `bandLabel` e `text` dizem o que ela vale e faz agora; `terms` e `breakdown` são a conta que a **próxima** virada vai fazer e somam `next.value`. Por isso a lista de termos tem o total com a faixa de `next` ("= 40 Inquieto, na próxima virada do dia"), e nunca é apresentada como a explicação do número de agora.
- **Cabeçalho** (`components/Header.tsx`, nas abas Feudo e Hoje): "Moral 60 (Contente): produção × 1,05", com o ícone da faixa e, quando a virada vai mudá-la, "· na virada do dia, cai para 40 (Inquieto)". A queda leva seta para baixo, verbo e o tom de aviso; a subida, seta para cima, sem alarme. O que a moral faz com a produção é o resto da frase `text` (`moraleEffect`); se a frase mudar de forma, o cabeçalho fica só com o número e a faixa. A explicação do número (`moraleExplanation`) junta `text`, `nextText`, a conta com o prazo ("daqui a 30 min") e `advice`.
- **Um ícone por faixa** (`moraleIcon`): `thumbsdown`, `comment-discussion`, `smiley` e `star-full`, do pior para o melhor. O nome da faixa está sempre ao lado: nada é dito só pelo ícone nem só pela cor. Nenhum deles é o da fome nem o do frio. O ícone ganha o tom de aviso quando a moral está tirando produção (`multiplierPercent` menor que 100).
- **Painel "Moral"** (`components/Panels.tsx`, entre Trabalhadores e Recrutar): a frase de agora; `nextText` com a contagem regressiva de `nextUpdateInSeconds`; a lista de termos (o primeiro, a base, sem sinal; os outros com "+" ou "−" no texto) e o total, que se explica pelo `breakdown` (é onde aparece "a moral não desce de 0"); os efeitos passageiros com o que falta para acabarem; o conselho; a frase da comida guardada (`foodReserve.text`, omitida quando o conselho já é ela); e `notes`.
- **O conselho** (`advice`) leva o sinal de aviso quando algo pesa na conta (há termo negativo) e a lâmpada quando é só o caminho para um bônus. É decisão de apresentação: o texto é sempre o do servidor.
- **Na fome, um segundo aviso** logo abaixo do de fome (`FamineBanner`, em `components/Banners.tsx`) traz `morale.notes`: em quanto tempo alguém deserta, a chance de alguém partir, o piso que segura os últimos. A perda é anunciada antes de acontecer. É `role="note"`, não região viva: o prazo muda a cada leitura.
- **Recrutar** mostra `recruitment.moraleNote` abaixo do custo e antes dos botões, e a lista da paleta o repete no texto do campo.
- **Árvore** (`ui/treeModel.ts`): a linha "Moral", a última do feudo antes da Lareira, com "60 (Contente) · ⚠ cai para 40 (Inquieto)". A explicação é a do cabeçalho, uma frase por linha, mais as `notes`. O clique só navega.
- **Avisos** (`notifications/policy.ts`): `villagerLeft`, `villagerDeserted` e a mudança de faixa **para pior** são alarmes (nível "Essenciais", tom de aviso); a mudança para melhor é o alívio deles (mesmo nível, tom de informação); `villagerArrived` é boa notícia e avisa em "Todos", como a chegada de um recrutado. O sentido da mudança sai de `data.morale` e `data.previousMorale` do evento (`moraleBandDirection`): o app não compara faixas. O ícone da mudança de faixa é o da faixa nova; quem parte ou deserta sai com `sign-out`, e o colono, com `person-add`.
- **Relatório de Retorno** (`game/returnReport.ts`, `components/Today.tsx`): `counts.settlersArrived`, `villagersLeft` e `villagersDeserted` contam os eventos da ausência, e `morale` guarda a de agora e a da visão guardada. A tela diz "Moral 16 (Desesperado): caiu de 28 (Inquieto)." e, quando houve perda, a moral caiu ou algo ainda pesa nela, o conselho da visão de agora com o botão "Ver a moral". Quem chegou e quem se foi está nos blocos, somado, cada frase com o porquê (`peopleMoved`): os colonos e os recrutas em "O feudo prosperou", quem partiu e quem desertou em "O que exigiu um preço".
- **A explicação de um número do cabeçalho passa por cima dos avisos do canto.** O cabeçalho é fixo e tem a própria pilha; enquanto uma explicação dele está à vista (`:has(.explained:hover)` ou `:focus`), ele sobe acima dos avisos e continua abaixo dos diálogos.
- **Cache**: `morale` e `recruitment.moraleNote` são obrigatórios no schema; a visão guardada pela versão anterior é descartada sem mexer em `VIEW_FORMAT`, e o relatório dessa primeira volta sai sem a moral de antes.

## "Antes de partir", o aviso de estação e a prioridade da barra (GDD §2.3 e §13.5)

Nenhuma regra nova: tudo sai de prazos, taxas e estoques que o `ViewState` já traz. Os limiares abaixo (um dia, oito horas, uma hora) são escolhas de apresentação, em horas de relógio, como o destaque de "cheio em"; o app não converte tempo de jogo.

- **`beforeLeaving(view)`** (`game/beforeLeaving.ts`, função pura) devolve até cinco itens `{ id, severity, text, command }`, nesta ordem: a incursão que os vigias avistaram (só para quem tem a Torre; ver "Incursões, Paliçada e feridos"), a comida (fome em andamento, ou a comida que acaba em menos de 24 h, pelo prazo de `runsOutIn`: quando ele vem da previsão da estação que vem, o item diz a estação, o saldo que ela traz e o prazo, "Inverno em 1 h: o saldo de comida passa a −18,5/h, e ela acaba em 8 h."), a lenha (frio em andamento; no inverno, a madeira com prazo para acabar; antes dele, `calendar.nextFirewoodSeason` a menos de 24 h com `firewood.missing` maior que zero, seja o inverno a próxima estação ou a seguinte), um item por depósito cheio e perdendo ou a menos de 8 h de encher (a madeira e a pedra dividem o Armazém: um item), as obras que não começam sozinhas e os aldeões livres. Abaixo de 8 h, o que acaba é `danger`; o resto é `warning`; obras e aldeões livres são `info`.
- **Todo item tem um comando**, com o rótulo do botão: `lords.allocateWorkers` com o edifício que produz o recurso ("Alocar na Fazenda", "Alocar na Serraria"), `lords.build` com o depósito ("Construir Celeiro", "Ampliar Armazém"), `lords.planConstruction`, `lords.toggleAutoStart`. Quando a obra do depósito está travada ou já em curso, o botão é "Ver os depósitos" e leva ao feudo, onde o aviso do depósito tem o custo e o motivo.
- **A fome e o frio que acabam sozinhos.** Quando a visão traz `famine.endsInSeconds` ou `winter.cold.endsInSeconds` (quem chegou ao ofício ainda se adapta), o item deixa de ser urgente e de oferecer "Alocar na Fazenda": diz o prazo ("A fome já dura 40 h, mas acaba sozinha em 2 h. Não é preciso mexer na Fazenda.") e o botão leva ao feudo. Os avisos de fome e de frio (`components/Banners.tsx`) também deixam de acrescentar "Ponha aldeões na Fazenda": a frase do servidor já diz o porquê e o prazo.
- **Quanto falta de lenha é a conta do servidor** (`firewood.missing`), que já desconta o que a Serraria repõe e o que as obras planejadas automáticas vão levar do estoque (`firewood.reserved`). Quando há obra levando madeira, o item diz quanto ("As obras que começam sozinhas levam 80 do estoque."). O app não divide o estoque pela taxa.
- **A lista é honesta nos dois sentidos.** Com a obra do depósito em curso e pronta antes de ele encher, o item some: não há mais o que fazer. Uma planejada automática que espera algo que chega (recurso, fila, outra obra) é o feudo preparado; uma que espera o que esperar não resolve (`waiting.etaSeconds` nulo: não cabe no depósito, falta o Salão) vira item, com a frase do servidor. Com as filas ocupadas, a obra que termina em menos de 8 h sem nada depois também é dita.
- **Na aba Hoje** (`components/Today.tsx`, `BeforeLeaving`): abaixo do Relatório de Retorno, ou no topo quando não há relatório. Com o relatório à vista, não repete o que o bloco "Você ainda pode decidir" já traz com a mesma frase e o mesmo botão (`beforeLeaving(view, skip)`, com `coveredTopics`); se tudo já está lá, diz isso em vez de "preparado". O que custou não tira nada daqui: o relatório conta a perda da ausência, e esta seção, o que está acontecendo agora. Uma linha por item, com o botão ao lado (abaixo, em tela estreita). A urgência tem ícone e uma palavra para leitores de tela ("Urgente", "Atenção", "Sugestão"); a cor só reforça. Sem itens: "O feudo está preparado para a sua ausência." Sem ligação, os botões que dão ordens ficam desabilitados; o que só navega continua. **Sem ligação a seção não garante nada**: a visão é a guardada, que pode ter horas. A lista vazia diz "Sem ligação com o reino: este é o último estado conhecido do feudo. Nele não havia nada a preparar; confira de novo quando a ligação voltar.", com o ícone de alerta no lugar do visto, e a lista com itens avisa que eles e os prazos são os do último estado conhecido. Vazio e sem ligação são estados diferentes, com frases diferentes.
- **Na árvore**, a linha "Hoje em …" diz quantos itens esperam ("2 a preparar"; "⚠ 3 a preparar" quando algum é mais que sugestão; "pronto para a ausência" sem nenhum), e a explicação os lista: quem está no feudo sabe que há o que ver na aba Hoje. As novidades e a falta de ligação passam na frente; sem ligação, a explicação também diz que fala do último estado conhecido, e não que o feudo está preparado.
- **Aviso de estação, uma hora antes** (`seasonAhead`, em `notifications/policy.ts`): quando `calendar.nextSeason.secondsUntil` chega a uma hora, "Inverno à vista: chega em 59 min, às 21:40." e, em lista, as frases de `nextSeason.changes`. Se a estação que vem queima lenha e a conta não fecha, entra a frase da conta (`firewood.text`) e o aviso ganha o tom de alerta; o mesmo quando a comida acaba na estação que vem (`food.depletesInSeconds` com prazo): entra `food.text`. Não prevê sorteio nem promete nada: só repete a visão. "Ver" leva à aba Hoje, onde "Antes de partir" diz o que preparar.
- **A hora do relógio** é o prazo somado ao relógio do navegador, no fuso dele: o aviso fica na tela até ser dispensado, e "em 59 min" envelhece; a hora, não.
- **É um aviso por virada.** A marca (`"1:winter"`) fica em `seasonWarned`, junto do cache da partida (`GameSession.markSeasonWarned`): recarregar a página não o repete, e sair da conta a apaga com o resto. Só uma visão lida do servidor nesta abertura conta (`GameSession.live`): a guardada pode ter horas. Segue a política dos outros avisos (`decideNotice`): nada no nível silencioso e no modo discreto, contador durante o "Silenciar 2h" e quando as três da hora já saíram.
- **Na virada**, o evento `seasonChanged` avisa no nível "Essenciais", sem tom de alarme, com o ícone do calendário e as mesmas frases. Depois da virada a visão já fala da estação seguinte; por isso o controlador guarda as frases de cada estação enquanto ela é a próxima (`seasonChanges`). Sem elas (página aberta depois da virada), o aviso diz `calendar.seasonEffects`. A virada para uma estação que já passou (um salto longo com a aba ao fundo traz duas) não vira aviso. O aviso de uma hora antes, se ainda estiver à vista, sai de cena.
- **As frases que detalham um aviso** são `Toast.details`, desenhadas como lista abaixo do texto; a notificação do navegador as leva na mesma linha.
- **Barra de status** (`statusBar`, em `ui/format.ts`): sem ligação > incursão que os vigias avistaram (`$(megaphone) Lobos em 16 min`; ver "Incursões, Paliçada e feridos") > decisões pendentes (as cartas do Conselho, com o prazo da que vence primeiro; o clique leva à aba do Conselho) > fome e frio > depósito cheio e perdendo, ou a menos de 8 h de encher (`$(archive) Madeira: cheio em 3 h`; o clique leva ao feudo) > obra > comida por hora. Só a fome e o frio têm o destaque de aviso. Com mais de um depósito em alerta, a linha fala do que mais perde (ou do que enche primeiro) e a explicação, de todos.
- **Título da aba do navegador** (`documentTitle`): o contador (novidades e decisões pendentes, somadas), o mesmo assunto da barra e o nome do feudo ("(1) Habitações Nv2 · 00:04 · Pedra Alta · Lords of the Guild"). Com carta do Conselho à espera, o assunto é o próprio contador: "(1) Pedra Alta · Lords of the Guild". Sem ligação fica só o nome: o estado guardado pode estar velho. Com a aba ao fundo o relógio da página não anda, e o prazo do título é o da última leitura (a cada 2 min).
- **O modo discreto** continua só com o contador, na barra e no título.

## O Conselho do Feudo (GDD §7 e §13.2 a §13.6)

As cartas, o custo e a consequência conhecida de cada opção, a pista, o que a tranca, o prazo em tempo real, o que o conselho faz sozinho, quando vem a próxima audiência e a regra em uma frase vêm prontos em `council` e `pendingDecisions` do `ViewState`. O app não conhece a cadência das audiências, o limite de cartas à espera nem o prazo de resposta, e nunca vê o efeito escondido de uma opção. As frases de ligação e as escolhas de apresentação ficam em `ui/council.ts`.

- **A aba Conselho** (`tabs/Council.tsx`, `#/conselho`) é fixa, como a do Feudo, e leva o número de cartas à espera, com rótulo por extenso. Mostra o cabeçalho do feudo (a moral é o que as cartas mexem), o estoque em uma linha ao lado dos custos, uma folha por carta, a próxima audiência e a regra (`rulesText`), e "O que o conselho registrou": as linhas da Crônica que falam das cartas (`councilRecord`), da mais nova para a mais antiga, onde a resposta dada há um instante aparece contada.
- **O registro tem a sua própria conta** (`controller.councilLog`, `CouncilLog` em `ui/council.ts`). Não sai das 20 linhas da Crônica recente: uma carta espera 24 h na mesa, e nesse tempo a Crônica escreve bem mais que 20 linhas (obras, recrutas, feridos, marcas da Ameaça). A abertura lê as últimas 200 linhas da Crônica (`CHRONICLE_LOOKBACK`), tira delas a Crônica recente e as linhas do conselho, e os eventos que chegam depois entram nas duas listas. Sem linha a mostrar, a seção diz por quê (`councilRecordEmpty`): "Nada ainda" só quando a leitura chegou ao começo da Crônica; com as linhas do conselho antes do trecho lido, ou com a leitura falhando, ela aponta a Crônica inteira; sem ligação na abertura, diz que o registro vem da Crônica. A leitura se repete quando a ligação volta e quando a aba do Conselho é aberta.
- **A carta** (`components/CouncilCard.tsx`) é para ler antes de decidir: título e texto em letra de leitura, com serifa e linhas curtas; de onde a história vem, quando é continuação (`followsFrom.text`); as opções lado a lado (uma embaixo da outra em tela estreita). Cada opção é o botão com o verbo e, logo abaixo, `effectsText` (o custo e a consequência conhecida, na frase do servidor), a pista em itálico e, se houver, o que a impede: o requisito (`lockedReason`, com cadeado) ou o que falta para pagar (`optionMissing`, com os `missing` do custo). O botão aponta para tudo isso (`aria-describedby`). A opção que o conselho aplica sozinho é dita por extenso ("Sem resposta, é isto que o conselho faz."), e o pé da carta traz `expiryNote`.
- **Um caminho só de comando.** O painel, a árvore e a paleta chamam `controller.runCommand('lords.answerCard', …)`: o painel manda `{ instanceId, optionId }` do botão clicado; a árvore, a linha da carta (`card:<instanceId>`), e a lista pergunta a opção; a paleta ("Lords: Decidir carta do Conselho") pergunta a carta, quando há mais de uma, e depois a opção. Todos terminam em `controller.answerCard`, que fixa o `commandId` com `prepare`: "Tentar de novo", depois de uma falha de rede, reenvia a mesma ordem. Enquanto a resposta não volta, a carta fica em `controller.answering`, os botões dela ficam desabilitados e um segundo clique não vira ordem.
- **A lista das opções** (paleta e árvore) traz o texto da carta no alto (`PickOptions.detail`, que também descreve o diálogo), com o prazo e `expiryNote`. O que já vem marcado é a opção que o conselho aplicaria sem resposta, que nunca custa nada: `Enter` sem ler não gasta. Uma opção trancada ou sem recursos aparece com o ícone e o motivo; se for escolhida, a ordem segue, e quem recusa é o servidor, com o motivo de agora.
- **Recusas.** `CARD_NOT_PENDING`, `CARD_EXPIRED`, `INVALID_OPTION`, `OPTION_LOCKED` e `INSUFFICIENT_RESOURCES` chegam como qualquer recusa do motor: aviso com a frase do servidor, e a visão que veio na recusa toma a tela. A carta respondida em outra aba ou já expirada some.
- **Estados, cada um com a sua frase:** sem cartas ("O conselho não tem nada a tratar agora." e a próxima audiência); sem assunto para o feudo como ele está e mesa cheia (as frases são `council.note`, do servidor: com duas cartas, o conselho espera uma resposta antes de trazer outra); sem ligação (modo leitura, pelo último estado conhecido, com os botões desabilitados); resposta a caminho ("Levando a sua decisão ao conselho…"); prazo vencido no relógio da página antes de o servidor contar o que foi feito (botões desabilitados, "O prazo acabou: o conselho está decidindo sozinho"); sessão encerrada com a resposta a caminho ("A sessão terminou antes de a resposta chegar ao conselho. A carta continua à espera").
- **A carta sai da mesa com a lista aberta.** A lista fecha sozinha (`PickOptions.signal`), nada é enviado e um aviso diz por quê: o prazo acabou, outra aba respondeu, ou a sessão terminou. Quem distingue o prazo da outra aba é o relógio da página: o instante em que o prazo da carta vencia, com uma folga de dez segundos.
- **O prazo** é sempre de relógio e vem em `expiresInSeconds`. `expiresIn` (`ui/format.ts`) é o mesmo texto em todo lugar, "expira em 14 h", arredondado para baixo e descontado o tempo desde a leitura. A menos de 8 horas (o limiar de "cheio em": uma ausência comum) ganha o sinal de aviso, com ícone e texto: na carta, na aba Hoje ("Atenção:") e na árvore ("⚠ expira em 3 h"). A leitura seguinte do servidor acontece quando o prazo de uma carta vence e quando chega a próxima audiência (`nextPollMs`).
- **Árvore** (`ui/treeModel.ts`): "Conselho · 1 carta pendente (expira em 14 h)", com uma linha por carta; a explicação da linha é a regra e a próxima audiência. O clique leva à aba do Conselho; o botão "Decidir" da linha abre a lista das opções. A linha "Hoje em …" diz "● 1 decisão pendente", na frente das novidades. **Nada da árvore é cortado** (`.tree-text`, em `workbench/workbench.css`): a barra lateral tem largura fixa, e a descrição que não cabe ao lado do nome desce para a linha de baixo, em vez de sumir nas reticências; o texto longo quebra. O prazo de uma carta, "⚠ expira em 2 h" e "incursão a caminho" se leem sem passar o mouse. O teste em navegador confere que nenhum nome nem descrição da árvore passa da caixa (`cutTreeRows`, em `tests/e2e/helpers.ts`).
- **Aba Hoje** (`components/Today.tsx`, `PendingDecisions`): uma linha por carta, da que vence primeiro à última, com o prazo e o botão "Decidir", que leva à aba do Conselho. Depois de uma ausência a ordem é a do GDD §2.3: o Relatório de Retorno, com as cartas à espera no terceiro bloco dele ("Você ainda pode decidir"), e "Antes de partir". Sem relatório, as decisões abrem a aba quando há alguma, e fecham quando não há.
- **Barra de status**: `$(law) 1 decisão pendente · expira em 14 h`, com o prazo da carta que vence primeiro; a explicação diz o título e o prazo de cada uma; o clique leva à aba do Conselho. Não tem o destaque de alarme.
- **Título da aba do navegador e ícone do Feudo**: as decisões pendentes entram no contador, somadas às novidades: "(1) Pedra Alta · Lords of the Guild" e "Feudo: 1 decisão pendente". Com carta à espera o título fica com o contador e o nome, sem outro assunto. Sem ligação a carta é a do estado guardado, que pode já ter saído da mesa: não entra no contador, no badge nem na linha "Hoje" da árvore.
- **Aviso de carta nova** (`notifications/policy.ts`, `controller.notifyCard`): `cardDrawn` avisa no nível "Essenciais", sem tom de alarme, com o texto "Nova carta do Conselho: <título>", o prazo com a hora do relógio em que ele acaba ("por 23 h, até amanhã às 08:20": o aviso fica na tela, e "por 23 h" envelhece; `clockDeadline`, em `ui/format.ts`), `expiryNote` e os botões "Decidir" (leva à aba do Conselho) e "Silenciar 2h". A carta é a da visão, pelo `instanceId` do evento: se ela já saiu da mesa, o aviso não sai. O aviso some quando a carta é respondida ou expira, e quando o jogador chega à aba do Conselho; com essa aba à vista, a carta nova nem ganha aviso. Não entra no contador de novidades (nem durante o silêncio de 2 horas, nem com as três da hora já exibidas): quem a conta é o contador de decisões.
- **Os outros acontecimentos do Conselho**: `cardExpired` (o conselho decidiu sozinho) e `cardEffectApplied` (o que a opção escondia aconteceu) avisam no nível "Todas", com a frase da Crônica. `cardAnswered` não é notificação; a resposta dada **nesta aba** mostra, por alguns segundos, a frase que a escolha escreveu na Crônica (`tellOwnAnswers`): é o desfecho da carta.
- **Modo discreto**: nenhum aviso, a barra e o título só com o contador de tempo, e o ícone do Feudo sem badge. Dentro da bancada (árvore, aba, aba Hoje) a carta continua lá.
- **Versão nova no servidor**: `426 UPGRADE_REQUIRED` vira o aviso "Há uma versão nova do jogo. Recarregue a página.", com o botão "Recarregar", uma vez só. O cache gravado por outro protocolo é descartado pela marca de versão (ver abaixo).

## Ameaça e Torre de Vigia (GDD §8.2)

A Torre de Vigia compra informação. Sem ela, o servidor **não manda** o número da Ameaça, a tendência, as origens, os tiles nem a incursão marcada: `ViewState.threat` é uma união de duas formas fechadas, e o app confere `threat.known` antes de procurar qualquer número. O app não conhece quanto a Ameaça sobe por dia, as marcas da Crônica, a chance de uma incursão nem a antecedência do aviso. As frases de ligação e as escolhas de apresentação ficam em `ui/threat.ts`.

- **O painel "Ameaça"** (`components/ThreatPanel.tsx`) fica na aba Feudo, logo depois das Construções, onde a obra da Torre está listada.
  - **Sem a Torre:** a frase da névoa (`threat.text`), com o olho fechado; o que a Torre daria (`watchtower.next`), o custo e o prazo da obra e o botão "Construir Torre de Vigia" na mesma caixa; e a defesa (`defense.text`), com a obra da Paliçada ao lado. Nenhum número, nenhuma barra, nenhuma origem, nenhuma chance: nada disso chegou. `watchtower.text` no nível 0 repete a névoa e só entra na explicação da linha da árvore.
  - **Com a Torre:** `threat.text` ("Ameaça 46 de 100.") com a barra (`<progress>`, de zero a `max`, com rótulo); a tendência (`trend`), com seta, verbo e a contagem regressiva de `nextRiseInSeconds`; as origens, uma por linha (`sources`); "O que ronda o feudo:" com os tiles e se estão ativos, por extenso: é a pergunta da névoa, agora com resposta; o que os vigias avistam; a defesa, com a obra da Paliçada; e por fim o que a Torre faz (`watchtower.text`), o que o nível seguinte acrescenta e a obra dele.
  - **A incursão à vista** (`incoming`): um aviso com ícone próprio (`megaphone`), a frase do servidor (que no nível 2 da Torre diz o tamanho) e a contagem de `inSeconds`. Só a frase é região viva; a contagem muda a cada segundo e fica fora dela. Sem incursão: "Os vigias não avistam nenhuma incursão agora." O que o aviso traz além disso está em "Incursões, Paliçada e feridos".
- **A obra da Torre** (`watchtowerWork`, a partir de `constructions`): na lista do que pode ser construído (o botão, com o custo de `available[]`; bloqueada, desabilitado, com o motivo do servidor em uma linha própria, com cadeado; planejada, com a espera do servidor); em uma fila ("Torre de Vigia → Nv1 em obras: termina em 11:42. Até lá, ninguém vê.", sem botão); ou sem obra a ordenar (o teto desta versão: a frase do servidor diz por quê). O botão chama `lords.build` com `watchtower.building`: construir e melhorar são a mesma ordem, `startConstruction`.
- **O nome da Torre nunca é escrito no app**: vem de `constructions.available[].label` ou da fila. É um texto de `@lotg/content`, e `bundle.test.ts` barra frases do conteúdo no pacote.
- **Árvore** (`ui/treeModel.ts`): a linha "Ameaça", depois da Moral e antes da Lareira. Com a Torre, "46 · Covil de Lobos" (o número e os tiles ativos) e o olho aberto; com incursão à vista, "46 · ⚠ Lobos em 16 min". Sem ela, "desconhecida · sem Torre de Vigia" (ou "… em obras") e o olho fechado. A explicação é a do painel, uma frase por linha (`threatLines`). O clique só navega. Sem a Torre, e com a obra liberada, a linha ganha o botão "Construir" (`lords.threatBuild`), com o nome da obra no rótulo (`TreeNode.actionLabels`) e o custo na dica; `lords.build` reconhece a linha `threat` e ordena a obra que a linha oferece, sem abrir a lista. Com a obra travada não há botão: a explicação diz o motivo. Com a Torre de pé, o botão passa a ser o da Paliçada (ver "Incursões, Paliçada e feridos").
- **A Torre na lista de obras** (`ConstructionsPanel.tsx`) não tem nada de próprio: entra em "Construir" (nível 0) com `effect` ao lado do custo, travada com o motivo até o Salão chegar ao nível 2; erguida, passa a "Melhorar"; no nível 2 sai da lista.
- **O relato dos vigias** (`threatRose`, em `notifications/policy.ts`): a Ameaça cruzou uma marca. Só chega a quem tem a Torre. Avisa no nível "Essenciais", sem o tom de alarme (nada se perdeu: é hora de se preparar), com o olho da Ameaça e a frase da Crônica; com pouco espaço fica junto das cartas novas e das viradas de estação, atrás dos alarmes. "Ver" leva ao Feudo. Um relato novo (outra marca, ou os uivos) toma o lugar do que está na tela: "A Ameaça chegou a 40" não fica ao lado de "chegou a 70" (`controller.watchToast`). É linha da Crônica recente. No Relatório de Retorno não entra em bloco nenhum: fica em "A Crônica da ausência" (as incursões e o lugar delas no relatório são de V2E-T3).
- **Cache**: `threat` é obrigatório no schema; a visão guardada pela versão anterior é descartada sem mexer em `VIEW_FORMAT`. Uma visão sem Torre que trouxesse o número também não passa: a forma da névoa é fechada.

## Incursões, Paliçada e feridos (GDD §8.2 e §12.3)

É a primeira vez que o mundo faz algo contra o feudo, e a regra é a do GDD §12.3: a derrota custa pouco e ensina a Paliçada. Tudo vem pronto do servidor: a chance de uma incursão, o que cada tamanho de ataque custa, o aviso dos vigias com o que o ataque que vem custa e o que a Paliçada faz a ele, os feridos com o prazo para sararem, e as frases da Crônica, que contam como o bando chegou, o que levou e o que o teria detido. O app não conhece o estrago de um ataque, a antecedência do aviso, o que cada nível da Paliçada segura nem quanto dura um ferimento.

- **A defesa, com a obra ao lado** (`Defense`, em `components/ThreatPanel.tsx`): o que protege o feudo hoje (`defense.text`), o que a próxima obra da Paliçada passa a segurar (`defense.next`), o custo e o prazo dela e o botão "Construir Paliçada" ou "Melhorar Paliçada" (`lords.build` com `defense.building`). Travada, o botão fica desabilitado, com o motivo do servidor (antes do Salão Nv3, o do Salão); em obras, a contagem toma o lugar do botão; no teto desta versão não há obra, e o motivo do limite é o fim da frase de `defense.text` ("A Muralha de Pedra chega em uma versão futura."). A Paliçada é conhecida com ou sem Torre: a caixa aparece nos dois casos.
- **A ordem do painel segue o que o jogador pode fazer.** Sem a Torre: a névoa, a Torre (a saída dela) e a defesa. Com a Torre: o número, a tendência, as origens, o que os vigias avistam, a defesa (é o que muda o desfecho de um ataque) e por fim a Torre.
- **A chance e o custo de um ataque** (só com a Torre): a regra das incursões em uma frase (`raidRisk`: a chance da próxima virada, o prazo até a chegada, o tamanho que a Ameaça traz e a queda), logo abaixo do que os vigias avistam; e, na caixa da defesa, o que cada tamanho custa a um feudo sem defesa (`raidCosts`, uma linha cada): o preço de não ter a Paliçada fica ao lado do preço dela.
- **A incursão à vista** (`incoming`): o aviso com o ícone da incursão (`megaphone`), a frase dos vigias e a contagem de `inSeconds`; o que este ataque custa (`costText`, com os números do estoque de hoje quando a Torre diz o tamanho) e, com o escudo, o que a Paliçada faz a ele (`defenseText`). A caixa da defesa vem logo abaixo: com a obra liberada, o prazo dela fica ao lado do prazo do ataque ("A obra leva 10 min; o ataque chega em 15:40.", `palisadeRace`). O app só põe os dois números lado a lado; **se dá tempo, quem diz é o servidor**, em `defenseText`, assim que a obra começa ("que fica pronta a tempo", "só termina depois dele"). Com o aviso à vista, a lista do que cada tamanho custa sai: o custo deste ataque já está dito.
- **A Paliçada na lista de obras** (`ConstructionsPanel.tsx`) não tem nada de próprio: entra em "Construir" com o que ela segura ao lado do custo (`effect`), travada com o motivo até o Salão chegar ao nível 3; erguida, passa a "Melhorar"; no nível 2 sai da lista.
- **Árvore**: o botão da linha "Ameaça" ordena a obra que responde a ela (`threatRowWork`, em `ui/threat.ts`): sem a Torre, a Torre; com ela (ou enquanto a obra dela não pode começar), a Paliçada. O botão diz "Construir" ou "Melhorar", com o nome da obra no rótulo e o custo na dica. A linha do feudo ganha "· incursão a caminho". A explicação da linha "Ameaça" traz a chance, o custo e a defesa, frase a frase (`threatLines`).
- **Feridos** (`population.injured`, `secondsToNextRecovery`, `injuredNote`, `workers[].injured`): moram e comem, mas não trabalham nem estão livres, e por isso ficam fora das duas contas ("Trabalhadores (10/12)", `employed`, em `ui/workers.ts`). No cabeçalho, "Feridos 2 (o próximo sara em 19:42)", com ícone próprio (`pulse`) e a frase do servidor como explicação; no painel dos trabalhadores, a mesma frase à vista e a marca em cada ofício de onde alguém saiu ("1 ferido: volta a este ofício quando sarar."); na árvore, "10/12 alocados · 0 livres · 2 feridos" e "· 1 ferido" no edifício; na lista "Alocar trabalhadores", as mesmas contagens. A moral leva o termo "Incursão sofrida" pelo mecanismo que já existia (termos e efeitos passageiros).
- **A leitura seguinte acontece quando a incursão chega e quando o próximo ferido sara** (`nextPollMs`, em `game/gameSession.ts`): o desfecho e a volta ao ofício aparecem na hora.
- **Avisos** (`notifications/policy.ts`): o alarme dos vigias (`raidAnnounced`) e o ataque sofrido (`raidSuffered`) são alarmes, no nível "Essenciais", com tom de aviso e o ícone da incursão. O alarme diz também quando o ataque chega, com a hora do relógio, o que ele custa e o que a Paliçada faz a ele (`raidAhead`, da visão); sai de cena quando o ataque chega (`raidToast`, no controlador), e nem aparece se a visão já não traz a incursão. O ataque sofrido diz quem ficou ferido e quando sara (`raidAftermath`). O ataque que a paliçada deteve (`raidRepelled`) é o alívio: mesmo nível, sem alarme, com o escudo. Os uivos (`wolvesHowl`) são um prenúncio: nível "Essenciais", sem alarme, só com a frase da Crônica (nenhum prazo, número ou tamanho), com o olho aberto ou fechado conforme o feudo tenha vigias. Quem se fere e quem sara não vira aviso: o ataque já contou, e o painel mostra. O alarme de uma incursão que o mesmo lote de eventos já traz resolvida não sai.
- **Barra de status e título da aba**: `$(megaphone) Lobos em 16 min` passa na frente de tudo, menos da falta de ligação. É o único assunto com prazo curto que se resolve sozinho (no máximo a antecedência da Torre), e foi para vê-lo antes que o jogador a ergueu; uma carta espera um dia, e a fome e o frio duram horas e têm o aviso deles no alto das abas. Não leva o destaque de alarme: a mesma linha anuncia o ataque que a Paliçada vai segurar, e o app não sabe qual é qual; a explicação traz o custo e a defesa. O clique leva ao feudo.
- **"Antes de partir"**: a incursão à vista abre a lista, com o aviso, o prazo e `defenseText`, e o botão da defesa (`defenseCommand`, em `game/beforeLeaving.ts`): a obra da Paliçada quando ela pode começar; senão, a da Torre de Vigia; senão, "Ver a defesa", que leva ao painel onde estão o custo e o motivo. Sem incursão à vista, a Ameaça que pode marcar uma na ausência também entra, logo no começo (`threatItem`): com a Torre, a chance acima de zero e a Paliçada abaixo do teto (`defense.next` não nulo), "Ameaça 85 de 100. A próxima virada do dia, em 40 min, tem 50% de chance de marcar uma incursão." e `defense.text`, com o mesmo botão da defesa; alerta sem Paliçada, informação com uma que segura parte dos ataques. Sem a Torre não há item: a lista não conta o que a névoa esconde. Antes disso, a aba Hoje dizia "O feudo está preparado para a sua ausência" com a Ameaça em 85 e nenhuma Paliçada.
- **"Ver a defesa" chega ao painel.** O painel da Ameaça fica abaixo da dobra da aba Feudo. `lords.openPanel` com o argumento `threat` (`THREAT_SECTION`, em `ui/threat.ts`) abre a aba e leva a página e o foco ao título do painel (`CommandEnv.reveal`, que `main.tsx` implementa com `scrollIntoView` e `focus` no quadro seguinte ao do desenho). O título vai ao alto da área da aba, logo abaixo do cabeçalho preso (`revealBelowHeader`), e não ao meio: o aviso da incursão e a obra da Paliçada, que vêm depois dele, ficam à vista, longe do canto de baixo onde ficam os avisos. E **seguir um aviso do jogo ("Ver", "Decidir") recolhe todos os avisos do jogo**, como "Silenciar 2h", sem silenciar os seguintes: um aviso com botões não some sozinho, e os que sobrassem ficariam por cima da coluna do painel. O que eles diziam continua no jogo (a Crônica recente, o contador de decisões, "Antes de partir", a barra de status). Usam esse caminho o botão "Ver a defesa" (em "Antes de partir" e no Relatório de Retorno), o clique na barra de status com uma incursão à vista e o "Ver" dos avisos que vêm da mata (uivos, relato dos vigias, alarme e desfecho). A linha "Ameaça" da árvore continua só navegando, com o foco na árvore: quem anda por ela com as setas não é levado embora.
- **Relatório de Retorno** (critério 4 do GDD §16.2): a incursão sofrida entra em "O que exigiu um preço", com a frase da Crônica (o que foi levado, quem se feriu, o que a teria detido) e o botão da defesa, refeito com a visão de agora; a que a paliçada deteve entra em "O feudo prosperou", sem botão; os feridos que sararam entram somados em "O feudo prosperou". A conta dos estoques ganha a coluna **Levado** (`resources[].raided`, a soma de `raided_<recurso>` dos eventos), só quando alguma incursão levou algo, e continua fechando: antes + produção − gasto + recebido − perdido − levado = agora. `produced` soma de volta o que foi levado: os lobos não comem a produção sem a tabela mostrar as duas coisas. `counts.raidsSuffered`, `raidsRepelled`, `villagersInjured` e `villagersRecovered` contam os eventos.
- **Sem a Torre nada disso existe antes do ataque**: a visão não traz incursão, chance nem custo, e o app não inventa nenhum. O jogador sem Torre fica sabendo pelos uivos (sem informação) e pelo ataque, cuja frase diz "sem que ninguém os visse vir" e aponta a paliçada.
- **Cache**: os campos novos de `population`, `workers[]` e `threat` são obrigatórios no schema; a visão guardada pela versão anterior é descartada sem mexer em `VIEW_FORMAT`.
- **O que não foi feito aqui:** a Ameaça não entra no cabeçalho como número (a incursão à vista tem a barra de status, a árvore, o aviso e "Antes de partir"); não há aviso no alto das abas para a incursão, como há para a fome e o frio.

## Objetivos do Senhor (GDD §12.2)

Os objetivos são o tutorial vivo: cada um aponta uma ferramenta no momento em que ela resolve um problema. Tudo vem pronto em `objectives[]` do `ViewState`: a ação (`title`), o porquê (`hint`), a recompensa (`reward`, a de moral já com o prazo em dias de jogo e no relógio de quem joga), o progresso, **o que falta agora** (`missing`) e onde o objetivo se cumpre (`target`). O app não conhece objetivo nenhum pelo id, a ordem da sequência, quantos ficam em aberto nem quantos ainda vêm. As frases de ligação e a escolha do comando ficam em `ui/objectives.ts`.

- **Três lugares, o mesmo desenho.** O painel "Objetivos" da aba Feudo (`components/ObjectivesPanel.tsx`), a seção "Objetivos" da aba Hoje, logo depois de "Antes de partir" (o mesmo componente, com `brief`), e o grupo "Objetivos" da árvore, o último do feudo. Em todos, só os objetivos em aberto ganham linha (o servidor nunca manda mais de três).
- **Cada objetivo em aberto** diz a ação, o progresso quando ele se cumpre aos poucos ("(1/3)"; "0/1" não aparece), o porquê, a recompensa e, na linha de baixo, o que falta: a frase do servidor, com o relógio de quem espera. Quando `missing` é nulo, só falta uma ordem: a linha diz "Só falta a sua ordem." ou, se a ordem é uma obra, "Pode começar agora: 80 madeira, 20 pedra · 4 min.", com a seta. O custo fica ao lado do prêmio antes do clique.
- **O botão leva até lá** (`objectiveAction`, pelo `target`): trabalhadores → "Alocar na Fazenda" (`lords.allocateWorkers`, com a prévia do que rende); edifício → "Construir Torre de Vigia" ou "Melhorar Habitações" (`lords.build`) quando a obra pode começar, "Ver as obras" quando está travada (leva a página e o foco ao painel das construções, onde estão o custo e "Planejar"), e nenhum botão com a obra em curso; recrutamento → "Recrutar aldeões" (`lords.recruit`), a menos que os que já estão a caminho bastem; conselho → "Decidir no Conselho" com carta à espera, "Ver o Conselho" sem nenhuma; planejadas → "Ligar o início automático" quando há uma planejada à espera de ordem, senão "Planejar obras"; estação → sem botão, porque atravessar o inverno é esperar. O nome dos edifícios vem da visão (`constructions.available[].label`, `workers[].label`).
- **O botão é descrito pelo objetivo inteiro** (`aria-describedby`): pode haver dois "Ver as obras" na mesma lista. Sem ligação, os botões que dão ordens ficam desabilitados; os que só navegam (`lords.openPanel`) continuam.
- **Os cumpridos** ficam recolhidos no painel do feudo ("Cumpridos (4)", um `<details>` que abre com `Enter`), com o porquê e a recompensa de cada um. Na aba Hoje viram uma contagem ("4 já cumpridos.") e o botão "Ver todos", que leva à lista do feudo.
- **Sem objetivo em aberto** a frase é "Nenhum objetivo em aberto agora: o que havia a cumprir está cumprido." Vale para o fim da sequência e para a leitura em que os objetivos seguintes ainda não foram revelados (uma partida que acaba de chegar de outra versão): a visão não diz quantos vêm, e a tela não promete nem lamenta.
- **Árvore** (`ui/treeModel.ts`): "Objetivos · 3 em aberto · 4 cumpridos", aberto, com uma linha por objetivo em aberto ("Recrute 3 aldeões · 1/3 · +40 comida"). A explicação da linha é o porquê, a recompensa e o que falta; a do grupo, os títulos dos cumpridos. O clique só navega. O botão da linha é o mesmo do painel, com a palavra curta ("Alocar", "Construir", "Ver") e, na dica, o custo da obra. É a linha que traz o botão (`TreeNode.action`, com o comando e o argumento), e não o tipo dela: `rowActions` (`workbench/Tree.tsx`) o devolve como veio, e o comando recebe o argumento declarado em vez da linha. Sem ligação, os botões da árvore ficam todos desabilitados, como os das outras linhas; o clique na linha continua navegando.
- **`lords.openPanel` com `objectives` ou `constructions`** (`OBJECTIVES_SECTION` e `CONSTRUCTIONS_SECTION`) abre a aba Feudo e leva a página e o foco ao título do painel, como já fazia com a Ameaça. Os dois títulos recebem foco (`tabindex="-1"`).
- **A recompensa de moral** não muda a moral na hora: entra como efeito passageiro na conta da próxima virada do dia, com o nome que o servidor deu ("O Senhor ouviu o Conselho", "Inverno sem frio"), e aparece no painel "Moral" pelo mecanismo que já existia (termos e "Passageiro: …").
- **Avisos** (`notifications/policy.ts`): `objectiveCompleted` continua no nível "Todos", agora com o visto (`pass`), e "Ver" leva à lista dos objetivos, onde os seguintes acabaram de aparecer. **Vários objetivos cumpridos no mesmo lote são um aviso só** (`objectivesCompleted`, em `ui/objectives.ts`): "3 objetivos cumpridos.", com uma linha para cada um e a recompensa como a visão a diz. Acontece quando o que o feudo já tinha feito conta de uma vez (o objetivo aparece já cumprido, e concluir um revela o seguinte). O lote gasta um dos três avisos da hora e conta como uma novidade.
- **Relatório de Retorno**: um objetivo cumprido na ausência fica com a frase da Crônica, em "O feudo prosperou"; dois ou mais saem em **uma linha**, onde o primeiro aconteceu: "2 objetivos cumpridos. Construa o Celeiro ou o Armazém: +60 madeira. Construa a Torre de Vigia: +40 pedra." A conta dos estoques, a contagem (`counts.objectivesCompleted`) e "A Crônica da ausência" continuam com cada um. O objetivo que a visão não traz (pelo `data.objective` do evento) fica com a frase da Crônica.
- **Cache**: `missing` e `target` são obrigatórios no schema; a visão guardada pela versão anterior é descartada sem mexer em `VIEW_FORMAT`.

## Relatório de Retorno em três blocos e "Sua escolha voltou" (GDD §2.3; roadmap da v0.2, V2D-T4)

É o momento em que o jogo fala com quem voltou: em uma leitura, o saldo da ausência e uma ação. Nenhuma regra de jogo: `buildReturnReport` (`game/returnReport.ts`, função pura) só agrupa os eventos que o servidor mandou e a visão de agora.

- **Os blocos** (`ReturnReport.blocks`, `packages/protocol/src/report.ts`): cada item é `{ text, topic?, severity?, action? }`, com a ação `{ command, arg?, label }` (um comando de `palette/commands.ts`).
  - **O feudo prosperou:** obras concluídas e edifícios erguidos, planejadas que começaram sozinhas, recrutas e colonos (somados, uma linha cada), ofícios dominados, objetivos cumpridos (vários, em uma linha só: ver "Objetivos do Senhor"), a fome e o frio que acabaram, a moral que subiu de faixa, e o efeito escondido de uma carta que não tirou nada (mesmo que o depósito tenha cortado parte do ganho). Sem botão: boa notícia não pede ação.
  - **O que exigiu um preço:** a fome e o frio que começaram (os que já vinham de antes e não pararam ganham uma linha sem número: "A fome continuou durante toda a sua ausência."), quem desertou e quem partiu (somados), a moral que desceu de faixa, as cartas que o conselho decidiu sozinho (a frase diz o que ele fez), o efeito escondido que cobrou algo (`spent_*` ou moral negativa no evento; a parte de um ganho que o depósito cortou, `lost_*`, não faz da boa notícia um preço: ela sai na linha do depósito), e o que foi ao chão, uma linha por depósito ("Despensa sem espaço: 120 de comida foram ao chão.", com o número da coluna Perdido). **Cada item tem a próxima ação** (`costAction`): a de "Antes de partir" para o mesmo assunto, se ele ainda pede preparo; senão, o caminho que evita a próxima (a Fazenda, a Serraria, a obra do depósito, a conta da moral, a mesa do conselho).
  - **Você ainda pode decidir:** as cartas à espera, com o prazo e, na continuação, a frase do servidor que lembra a escolha (`followsFrom.text`); depois as obras que não começam sozinhas e os aldeões livres, nas frases e com os botões de "Antes de partir" (`pendingItems`).
- **A ordem** dentro de cada bloco é a dos acontecimentos; o que é soma fica onde aconteceu o primeiro. O que não é desfecho (viradas de estação e de ano, ordens dadas em outro navegador, cartas que chegaram) fica fora dos blocos e continua em "A Crônica da ausência", recolhida abaixo da tabela (`<details>`), com todas as linhas.
- **O que é da ausência fica; o que é de agora acompanha o feudo.** O relatório guarda os blocos do instante em que foi montado, e a aba os desenha com `currentBlocks(report, view, elapsed)`: os dois primeiros não mudam, mas os botões das perdas e o terceiro bloco são refeitos com a visão de agora. A carta respondida sai da lista, o prazo desce com o relógio da página, e "Construir Celeiro" vira "Ver os depósitos" quando a obra começa.
- **Na aba Hoje** (`components/Today.tsx`): o tempo fora, a moral, os três blocos (cada um com título, ícone e contagem; vazio, diz o que não houve), a conta dos estoques, a Crônica da ausência e "Marcar como lido". O item que pede ação tem o desenho dos de "Antes de partir" (ícone e palavra da urgência, frase, botão ao lado; abaixo, em tela estreita), e o botão é descrito pela frase (`aria-describedby`): há mais de um "Decidir" na mesma lista. Sem ligação, os botões que dão ordens ficam desabilitados.
- **A aba que ficou aberta** (`gameSession.ts`, V2D-T4.4): sair de vista começa a contar uma ausência (`Away`: o instante, a visão que correspondia ao cursor e os eventos que chegarem em segundo plano). Na volta, com 4 horas ou mais fora de vista, ela vira Relatório de Retorno (`onReturnWhileOpen`); o app **não troca de aba debaixo do cursor**: um aviso diz "Você esteve fora por 5 horas. O Relatório de Retorno espera na aba Hoje.", com "Ver" (no modo discreto, só a marca na aba). A ausência vai para o cache (`away`), porque o navegador pode descartar a aba em segundo plano e recarregá-la na volta: aí o relatório sai como o de qualquer reabertura, contado desde que a aba saiu de vista. Se outra aba do mesmo navegador esteve à vista nesse meio-tempo (`attendedAt`, gravado por quem está à vista), o jogador não esteve fora, e não há relatório. **Limite:** a aba que ficou **à vista** o tempo todo (em um segundo monitor, a noite inteira) não tem como saber que o jogador saiu, e não recebe relatório.
- **Sem duplicar:** os eventos chegam pelo cursor (`GET /events?after=`), paginados até o fim, e cada um é entregue uma vez; a reconexão retoma do cursor, e o relatório só sai depois de uma leitura inteira.
- **"Sua escolha voltou" na Crônica** (`tabs/Chronicle.tsx`, `tabs/markdown.ts`): o servidor põe, no Markdown, um item recuado sob a linha de uma carta que continua outra, citando a linha do desfecho anterior: `  - Sua escolha voltou: “No 4º dia da Primavera, o senhor…”` (ou "A decisão do conselho voltou", quando quem escolheu foi o conselho). A ligação fica **em texto**: vale no arquivo baixado. `parseChronicle` lê a nota (`ChronicleLine.echo`) e acha a linha citada pela frase, a mais recente antes dela; a aba mostra a citação logo abaixo da continuação, e o botão leva o foco e a página à linha da escolha (cada linha tem a âncora `cronica-<n>`). Não é um link de endereço: o `#` da página é das abas.

## Cache e versões

O cache de cada partida (`lords.cache:<servidor>:<conta>:<partida>`) guarda `version`, que é `CACHE_VERSION` de `game/gameSession.ts`: o protocolo e o formato da visão (`VIEW_FORMAT`). Ao abrir, a visão só é exibida se a marca for a desta versão **e** a visão passar no `ViewStateSchema`; senão ela é descartada, e o cursor dos eventos e o instante da última visita são mantidos. Sem o cursor, a partida inteira voltaria como novidade. Com o instante, quem volta 4 h ou mais depois de uma atualização do jogo é tratado como em qualquer ausência longa: abre na aba Hoje, os eventos da ausência não viram avisos avulsos, e o Relatório de Retorno sai sem a tabela de estoques (não há visão antiga a comparar), dizendo por quê. A primeira leitura do servidor grava por cima. Suba `VIEW_FORMAT` quando um campo do `ViewState` mudar de sentido sem mudar de forma; mudança de forma o schema já pega, e mudança de protocolo muda a marca sozinha. Foi o caso das filas de obras e das planejadas automáticas (V2C-T5): os campos novos são obrigatórios no schema, e a visão guardada pela versão anterior é descartada sem mexer em `VIEW_FORMAT`.

**A visão e o cursor andam juntos.** O Relatório de Retorno compara a visão guardada com a de agora e soma os totais dos eventos desde o cursor (`lastSeq`): se a visão guardada já trouxesse o efeito de um evento que o cursor ainda não passou, o custo de uma obra sairia do estoque e entraria de novo como gasto. A visão chega antes dos eventos em dois lugares, e os dois cuidam disso (`game/gameSession.ts`):

- **Na resposta de uma ordem** (`adopt`), os eventos que levaram o mundo até aquela visão vêm no corpo. Quando começam logo depois do cursor, são entregues dali mesmo e o cursor anda com a visão, na mesma gravação: dar a ordem e fechar a aba deixa um cache coerente.
- **Na leitura do ciclo** (`pull`), e na resposta de uma ordem com um salto no cursor (outra aba ou o servidor agiram antes), a visão nova é gravada para o modo sem ligação com a que corresponde ao cursor ao lado, em `behind` (`null` se não há nenhuma). Lidos os eventos, `behind` some. Ao abrir, o relatório parte de `behind` quando ele existe; com `behind` nulo, sai sem a tabela de estoques.

Uma página de eventos que falha não leva as anteriores: o cursor já andou por elas, e os eventos delas são entregues antes de o erro subir.

O cache também guarda, enquanto a aba está fora de vista, a ausência em curso (`away`) e, sempre que uma aba à vista grava, o instante disso (`attendedAt`): é o que decide o Relatório de Retorno de uma aba que ficou aberta (ver a seção dele). Os dois são opcionais e não mexem na marca de versão; um `away` que não tenha a forma certa é ignorado.

## O que é próprio do navegador

- **Credenciais e cache** ficam no `localStorage` (chaves `lords.*`). O que as protege é a política de conteúdo de `index.html`: só arquivos da própria origem, nenhum script ou estilo embutido. Por isso não há `style="…"` em componente nenhum. No servidor de desenvolvimento a política é afrouxada para o Vite injetar estilos (`vite.config.ts`).
- **Várias abas** dividem o mesmo refresh token, que só vale uma vez. A renovação acontece dentro de `navigator.locks.request('lords.refresh')`; a aba que recebe o lock espera a gravação da outra chegar (`storageSettle`) e relê os tokens antes de decidir renovar. Sair, excluir ou perder a sessão em uma aba leva todas às boas-vindas.
- **Atalhos**: `Ctrl+Shift+P` e `Ctrl+P` são do navegador. A paleta abre com `F1` e `Ctrl+K`.
- **Nada chega com a aba fechada.** Com ela em segundo plano, o título conta as novidades e repete o assunto da barra de status; notificações do navegador só se o jogador ligar nas preferências, e a permissão só é pedida nessa hora.
- **Estado restaurado antes do primeiro desenho** (`main.tsx`): quem recarrega a página vê o feudo direto do cache, sem passar pelas boas-vindas.
- **A bancada ouve desde o primeiro desenho.** `useController` e o `DialogHost` assinam as mudanças com `useLayoutEffect`. Com `useEffect` a assinatura só existiria depois do próximo quadro, e o que mudasse nesse intervalo (a resposta de `/version`, um `F1` logo ao abrir a página) não redesenharia nada: a paleta ficava aberta sem aparecer e o texto digitado caía no campo das boas-vindas.

## Limites conhecidos

- O vínculo GitHub só foi exercitado com um GitHub simulado. O fluxo real depende de um OAuth App com *device flow* e do `GITHUB_CLIENT_ID` no servidor; sem ele o app esconde os botões. Na v0.1 o vínculo fica desligado em produção, por decisão do autor ([ADR 0010](../../docs/decisions/0010-version-informa-o-que-esta-ligado.md)).
- Testado só em Chromium. Firefox e Safari não foram abertos.
- A espera de `storageSettle` é uma proteção contra a leitura atrasada do `localStorage` entre processos do navegador; a corrida em si não foi reproduzida nos testes.
- Nome e ícone são provisórios. O texto de privacidade foi aprovado pelo autor em 2026-10-01.
